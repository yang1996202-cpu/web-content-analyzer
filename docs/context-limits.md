# AI 上下文预算说明

## 先说结论

AI 不是“看到链接就等于完整理解网页”。

更准确的说法是：

1. 工具可能可以 fetch 到完整内容。
2. 模型也可能有很大的上下文窗口。
3. 但长内容仍然会消耗预算、稀释重点、增加遗漏风险。

所以本项目不再强调“AI 只能读前多少”。真正应该强调的是：

> 内容越长，越需要先路由，再阅读。

## 什么是上下文预算？

上下文预算就是一次 AI 对话里可以放进去的信息总量。里面包括：

- 系统提示
- 历史对话
- 当前问题
- 工具返回内容
- AI 自己的中间分析和最终回答

即使模型窗口很大，也不代表你应该把所有东西都塞进去。长内容会让回答变慢、变贵，也更容易让关键细节被无关内容淹没。

## 为什么长文档要拆？

以安装开源项目为例，你真正需要的通常不是整份 README，而是：

- Requirements
- Installation
- Platform notes
- Configuration
- Troubleshooting

如果直接问“帮我安装这个项目”，AI 可能先总结项目介绍、功能列表、示例截图，却没有优先处理你最关心的安装条件。

更稳的问法是：

```text
请先找出这个项目文档里和安装有关的章节：
1. 系统要求是什么？
2. 安装步骤在哪里？
3. 不同操作系统有没有差异？
4. 有哪些常见报错和解决办法？
```

## 三个等级

| 等级 | 字符数 | 处理策略 |
|------|--------|----------|
| 安全 | < 3,000 | 可以直接读 |
| 注意 | 3,000-10,000 | 带着明确问题读 |
| 过长 | > 10,000 | 先问结构，再分块 |

这些阈值是经验值，不是数学定律。它们的作用是提醒你选择更稳的阅读方式。

## token 估算为什么只能粗略？

token 数取决于模型 tokenizer、语言、标点、代码、Markdown 结构。简单的“字符数乘固定比例”会在英文 README、代码块、Markdown 表格里明显失真。

本项目现在只给粗估值。要精确计算，需要接入目标模型对应的 tokenizer。

## 正确使用方式

### 短内容

```text
请阅读这个链接，总结重点。
```

### 中等内容

```text
请阅读这个链接里和安装有关的部分，不需要总结项目介绍。
```

### 长内容

```text
请先列出文档结构，并指出哪些章节和我的目标有关。先不要展开所有细节。
```

然后再继续问：

```text
只看 Installation 章节，告诉我具体安装步骤。
```

## 本项目的判断标准

Web Content Analyzer 的目标不是替你读完所有内容，而是在阅读前给出一个策略判断：

```text
这份内容适合直接读，还是应该先拆？
```
